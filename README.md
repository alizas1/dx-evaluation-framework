# Developer Experience Portfolio

By Aliza Solomon

How can we determine whether developers will succeed?

Most of the work in this portfolio grew out of that question.

The articles explore recurring patterns I encountered while reviewing APIs, validating implementations, developing review methodologies, and building systems designed to scale developer experience evaluation.

Together, they examine how developer experience issues emerge, how they can be identified, and how they can be addressed before they reach developers.

## Contents

### 1. Evaluating API Developer Experience

Introduces the framework used throughout the portfolio and the four layers of developer experience evaluation.

### 2. Mental Models

Examines how developers form assumptions about a platform and how those assumptions influence the decisions they make.

### 3. Nobody Starts From Your APIs

Examines how developers discover capabilities, choose solutions, and navigate platform complexity.

### 4. Information Validation

Looks at situations where developers understand what they need to do but lack information required to move forward successfully.

### 5. Real-World Validation

Examines issues that emerge only when realistic implementations are attempted.

### 6. Scaling Developer Experience Review

Documents the process I went through turning reviewer intuition into explicit evaluation criteria that could be taught, shared, and eventually incorporated into AI-assisted review systems..

## Finding Problems Before Developers Do

Most developer experience issues are visible before developers encounter them, if you know where to look.

The examples in this portfolio are drawn from years of API DX review, implementation validation, platform guidance, reviewer training, and AI-assisted evaluation work. Across those efforts, the same categories of issues appeared repeatedly.

Some became visible while developers were deciding which solution to use.

Others emerged when information was missing, assumptions were incorrect, or implementation exposed constraints that were not apparent during review.

Together, these examples explore where different types of developer experience issues emerge and how they can be identified before they reach developers.
